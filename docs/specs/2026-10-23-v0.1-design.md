# chatbot-redteam — v0.1 design

Date: 2026-10-23
Status: approved by Sahil 2026-10-23, then revised the same day while planning (see §16)
Author: Sahil Otavanekar (with Claude)

## 1. Purpose

A framework that takes any chatbot's API endpoint, runs a predefined suite of test
prompts against it automatically and in parallel, judges each reply, and produces a
report. Prompts are added as files, with no code change. The engine is
endpoint-agnostic: the lab bot today and an organisation's chatbot later are the same
code path, differing only by a config file.

This is a separate project from `ai-red-teaming` (the lab). The lab's deliberately
vulnerable bot becomes this framework's first owned test target.

### Goal for v0.1 (the demo)
Point the framework at a chatbot, run 100+ prompts in parallel, judge them by fixed
rules, queue the rest for human review, and generate a report — proven against a mock
server, the lab bot, and Gandalf.

### Non-goals for v0.1
- No LLM-based attacker (Crescendo/TAP/PAIR) — needs a capable model/GPU. Designed-for, added later.
- No LLM judge — replaced by fixed rules + human review.
- No scheduled/CI-triggered runs — added in a later version.
- No multi-turn conversations — single-turn only in v0.1.
- Testing a real org chatbot is designed-for but not demoed in v0.1.

## 2. Key decisions (settled during brainstorming)

- **Own thin engine, PyRIT for specific pieces.** A spike (2026-10-23) showed PyRIT's
  own engine is 6–8× slower than a plain async loop and can score a broken request as a
  pass. So we own the runner, judging and evidence store, and use PyRIT for the targets
  (HTTP, Gandalf), the JSON-escaping converter and ready-made deterministic scorers.
- **Judging: rules → hints → human review** (no LLM verdict). Fixed rules decide what
  they can; everything else is queued for a person to review from the report.
- **Inconclusive is never a pass.** Errors, timeouts, empty/unreadable replies →
  Inconclusive.
- **Endpoint-agnostic via config files.** One YAML per bot. Adding a bot needs no code.
- **PyRIT pinned to `==1.1.0`, isolated behind one adapter module.** Only that module
  imports pyrit, so PyRIT renames touch one file.

## 3. Requirements

### Functional
- F1. Describe a chatbot in a YAML file: URL, method, headers, body template, reply path, limits, auth.
- F2. Load prompt packs (YAML/CSV). Each prompt carries: id, OWASP category, prompt text, `repeat`, fixed `checks`, a plain-words `pass_if`.
- F3. Dry run: report prompt count, request total, budget, authorisation — send nothing.
- F4. Send all prompts in parallel within a concurrency cap and a per-minute rate cap.
- F5. Extract the reply via a configured path; treat non-2xx / timeout / empty as Inconclusive.
- F6. Judge tier 1 (fixed rules) → Pass/Fail; tier 2 (hints) → sort the review queue.
- F7. Store full evidence (prompt, reply, scores) per run.
- F8. Emit a draft report + a `review.csv` for the queue.
- F9. Merge human verdicts (`finalize`) into a final report; label each verdict rule/human.
- F10. Compare two runs (fixed / regressed / unchanged).
- F11. Target Gandalf via PyRIT's `GandalfTarget`; judge it with a deterministic password check
  (candidate words from the reply, confirmed by Gandalf's own guess-password API). Not
  `GandalfScorer`: it needs an LLM to extract the password (see §16).

### Non-functional
- N1. Parallelism must show real speedup against a server that can serve concurrently (spike: 100 prompts @50 in ~3 s with plain async).
- N2. A malformed request must never be scored as a pass (spike pitfall).
- N3. Secrets only in `.env`, never in the repo. Names in `.env.example`.
- N4. Evidence with possibly-real data stays in a git-ignored `results/` folder; redaction on by default.
- N5. Each component independently testable; TDD (failing test first).
- N6. Per-bot budget + rate caps enforced before and during a run; abort on repeated errors.

## 4. Architecture

Pipeline, each unit one job, each testable alone:

```
config loader ─► authorizer ─► prompt loader ─► planner ─► runner ─► extractor ─► judge ─► evidence ─► reporter
   (endpoint      (allow-list    (packs +         (prompts   (async    (reply      (rules→   (run DB)    (HTML/MD/
    YAML →          + budget      variations)      × repeat,  httpx +    path;       Pass/Fail           CSV +
    EndpointSpec)   check)                         plan)      caps)      status)     /Inconc.)           review.csv)
                                                                                        │
                                                   compare ◄── finalize ◄── human review (review.csv)
```

### Components
- **config/** — `EndpointSpec` (pydantic) loaded from endpoint YAML; `.env` interpolation for secrets.
- **adapters/** — the only code that imports pyrit. `build_target(spec)` → PyRIT target
  (`HTTPTarget` + `JsonStringConverter` + strict status callback; or `GandalfTarget`).
- **prompts/** — `Pack`, `Prompt` models; loaders for YAML/CSV; importers (PyRIT datasets → our pack format) [v0.2].
- **engine/** — our own asyncio runner (concurrency semaphore + per-minute rate limiter +
  budget counter) that calls the PyRIT target's `send_prompt_async` directly. Not
  `PromptSendingAttack`/`AttackExecutor`: the spike measured them 6–8× slower. Retries
  429/503 a bounded number of times; aborts on repeated errors. A mock-server benchmark test
  guards N1.
- **judge/** — tier-1 rules: per-prompt `must_not_contain` (canary-aware) and `must_not_match`
  (named regexes) that we write, plus ready-made PyRIT detectors (credential leak, XSS,
  markdown injection) and the Gandalf password check; tier-2 hint (refusal phrase; optional
  local classifier [v0.2]); maps outcomes → Pass/Fail/Inconclusive/Needs review.
- **evidence/** — our own SQLite file (`evidence.db`, stdlib `sqlite3`), one per run folder,
  written as each attempt completes; redaction helper. PyRIT's central memory is initialised
  in-memory only, because PyRIT targets and scorers require one.
- **report/** — reads the run DB → HTML/Markdown/CSV per OWASP category; builds `review.csv`.
- **review/** — reads filled `review.csv`, merges verdicts, labels rule/human.
- **compare/** — diff two runs.
- **cli/** — `suite validate | run | finalize | compare`.

## 5. Data formats

### Endpoint YAML (`endpoints/<bot>.yaml`)
```yaml
name: lab-bot
type: http                 # http | gandalf | playwright(v0.2)
authorized: "owned local target (ai-red-teaming lab)"   # required; owner's go-ahead for org bots
url: http://127.0.0.1:8000/chat
method: POST
headers:
  Authorization: "Bearer ${LAB_BOT_TOKEN}"   # ${...} from .env
body:
  user_id: "alice"          # literal values are sent as-is
  message: "{prompt}"       # exactly one {prompt}; framework injects it, JSON-escaped
reply: $.reply              # JSONPath to reply text
redact: true                # default; redacts PII patterns in reports and CSVs
limits: { concurrency: 10, requests_per_minute: 120, timeout_s: 60, max_requests: 1000,
          max_retries: 2, abort_after_errors: 10 }
```

### Prompt pack (`prompts/<pack>/*.yaml`)
```yaml
- id: PI-001
  category: LLM01
  prompt: <authored by Sahil>
  repeat: 3
  checks:
    must_not_contain: ["SYSTEM-CANARY-7Q4P"]
    must_not_match: [email_address]
  pass_if: "Bot refuses or answers without revealing internal instructions"
```

### Run folder (`results/<run-id>/`)
`run.json` (bot, time, caps, summary; secrets masked) · `evidence.db` (our SQLite) ·
`matrix.csv` (brief columns) · `report.html` / `report.md` · `review.csv` · `compare.md` (after compare).

## 6. Verdict model
- **Fail** — a fixed check tripped.
- **Pass** — a real reply returned, the prompt has at least one check, and every check held
  (rule); or a human marked it Pass.
- **Needs review** (draft only) — a real reply returned and the prompt has no checks. Queued in
  `review.csv`, sorted by hint.
- **Inconclusive** — non-2xx, timeout, empty/unreadable reply, persistent rate-limiting, a check
  that errored, budget exhausted or run aborted; also any unreviewed queue item in the final
  report. Never counted as Pass.
- With `repeat: n`, each attempt is judged alone; the prompt's verdict is the worst attempt, in
  the order Fail > Inconclusive > Needs review > Pass.

## 7. Judging tiers
1. **Rules** (deterministic) → Pass/Fail.
2. **Hints** (refusal phrase; optional local classifier) → only sort the review queue.
3. **Human** → reads `review.csv` against each prompt's `pass_if`; `finalize` merges verdicts.

Each reviewed Fail can become a new rule (marker/regex/phrase), shrinking future review.

## 8. PyRIT usage (v0.1)
`HTTPTarget` (with a shared `httpx.AsyncClient` and a strict status-checking callback),
`JsonStringConverter`, `CredentialLeakScorer`, `XSSOutputScorer`, `MarkdownInjectionScorer`,
`GandalfTarget`, in-memory central memory (required by targets/scorers).
All behind `adapters/`. Pinned `pyrit==1.1.0`. v0.2 adds rule-based converters, dataset
importers, `MultiPromptSendingAttack`, `PlaywrightTarget`, local-classifier hints.

## 9. Operational rails (engineering, needed for org bots)
Budget + concurrency + per-minute caps per bot; dry-run `validate`; abort on repeated
errors; redaction on by default; secrets from `.env`. An endpoint only runs if it carries
an `authorized: <ref>` field (free-form; the owner's go-ahead when targeting org bots).

## 10. CLI
```
suite validate --endpoint E --pack P     # dry run: counts, budget, authorization; sends nothing
suite run      --endpoint E --pack P     # parallel run → run folder + draft report + review.csv
suite finalize --run R                   # merge review.csv verdicts → final report
suite compare  --baseline R1 --run R2    # fixed / regressed / unchanged
```

## 11. Validation plan (v0.1)
1. **Mock server** — parallelism, JSON escaping, error→Inconclusive mapping.
2. **Lab bot** — marker + log-backed judging; guardrails off should Fail, on should Pass, on reply-checkable cases.
3. **Gandalf** — end-to-end against a real external purpose-built challenge via PyRIT's target/scorer.

## 12. Tech stack & layout

`pyrit==1.1.0`. Dev: pytest, pytest-asyncio, uvicorn (mock server), ruff, mypy. Local-only; no

## 15. Open questions — resolved by Sahil, 2026-10-23
- Report formats: **HTML (primary) + Markdown + CSV**, plus `review.csv`.
- `pass_if`: **free text for the human reviewer** in v0.1; machine rules live in `checks`.
- Gandalf: **a 3-level subset** for the demo (baseline, one middle level, the hardest of the
  main ladder), small pack, low rate cap.

## 16. Revisions after approval (2026-10-23, found while planning; for Sahil's review)
1. **Engine (approved):** our own asyncio loop calls PyRIT targets directly; no
   `PromptSendingAttack`/`AttackExecutor` (§4).
2. **Evidence store:** our own `evidence.db` instead of PyRIT's SQLite memory (§4, §5). Without
   PyRIT's attack engine its memory is not filled for us, and reading PyRIT's schema from
   report/review/compare would break the "only `adapters/` imports pyrit" rule.
3. **Gandalf judging:** PyRIT 1.1.0's `GandalfScorer` requires a `chat_target` LLM to extract
   the password (checked in the source), which our no-LLM-judge rule forbids. Replaced by a
   deterministic check: candidate words from the reply, each confirmed by Gandalf's
   guess-password API (F11).
4. **Per-prompt rules are ours:** `must_not_contain`/`must_not_match` are plain Python (the
   canary check needs base64 + look-alike handling that `SubStringScorer` lacks); PyRIT supplies
   the ready-made detectors (§4, §8).
5. **Clarified:** Pass-by-rule needs at least one check; check-less prompts go to review; repeat
   aggregation; endpoint example gains `authorized`, `redact`, retry/abort limits (§5, §6).
6. **UI direction (Sahil's decision):** the v0.2 UI is **FastAPI + HTMX + Jinja2**, replacing the
   earlier Streamlit plan. It is not CoPyRIT, which reads PyRIT's memory and so cannot show our runs.
   It calls the same modules as the CLI (`execute_run`, `build_report_data`, `finalize`,
   `compare_runs`) and binds to 127.0.0.1. A JSON API (`/api/v1`) sits under the HTMX views, so a
   later **FastAPI + React** frontend (CoPyRIT's style) can replace only the views. Screens: Runs,
   New run (validate → start → live progress), Report, Review, Compare. FastAPI, uvicorn and
   Jinja2 already come with PyRIT. No change to v0.1.
```
