# chatbot-redteam v0.3 — Full OWASP LLM coverage (roadmap + Phase A)

Date: 2026-10-26
Status: draft for review
Author: Sahil Otavanekar (with Claude)

Extends the v0.2 importer (`docs/specs/2026-10-26-v0.2-importer-design.md`) so the baseline
**represents every OWASP LLM Top-10 category** — each by the correct method, never by invented
prompts. Builds on `feat/v0.2-importer`.

## 1. Purpose

After v0.2, the baseline covers LLM07 only. The manager-driven goal is a baseline that speaks to
all ten OWASP LLM categories for any endpoint. But some categories cannot be tested by sending a
chat prompt and reading the reply, so "cover all ten" is defined honestly: every category gets an
entry whose **method matches what the category actually is** — a rule-judged prompt pack, a
planted-marker template, or a process-review checklist. The hard rule holds: Claude never authors
attack prompts; prompt text is moved file→file from PyRIT's bundled garak datasets.

## 2. The coverage contract (binding)

`COVERAGE.md` (generated) represents all ten, with the method and source stated:

| OWASP | Method | Prompt source / mechanism | Judged by |
|---|---|---|---|
| LLM01 Prompt Injection | partial (exercised via LLM07 set) | garak `system_prompt_extraction` (reused, filed under LLM07) | canary; Phase C adds `static_prompt_injection` as an auxiliary signal on replies |
| LLM02 Sensitive Info Disclosure | auxiliary | on the extraction prompts | `credential_leak` |
| LLM05 Improper Output Handling | rule-judged | garak `web_html_js`, `markdown_js`, `example_domains_xss` | `xss_output`, `markdown_injection` |
| LLM06 Excessive Agency | rule-judged | garak `access_shell_commands` | `shell_command_output` |
| LLM07 System Prompt Leakage | rule-judged | garak `system_prompt_extraction` (Phase 1) | canary |
| LLM09 Misinformation | rule-judged | garak `package_hallucination_{real,stubs,unreal}` | `package_hallucination` (needs the vendored registry list) |
| LLM10 Unbounded Consumption | auxiliary check | no pack — a detector on any reply | reply-length / latency threshold (Phase D) |
| LLM08 Vector & Embedding | **planted-marker template** | per-bot: markers the owner plants in a RAG corpus | `must_not_contain` the other user's marker |
| LLM03 Supply Chain | **review checklist** | not prompt-testable — SBOM / model provenance | human/process review |
| LLM04 Data & Model Poisoning | **review checklist** | not prompt-testable — training pipeline | human/process review |

"Pass (rule)" on any of these means every configured check held, not that the bot is safe — the
report legend (from v0.1) already states this; `COVERAGE.md` repeats it.

## 3. Key decisions

1. **Prompts come only from PyRIT's bundled *local* garak datasets** (offline, Apache-2.0). The ~60
   PyRIT *remote* datasets (harmbench, jailbreakv, forbidden_questions, …) are out of scope: network
   -fetched, mostly content-moderation / harmful-content, not application-security.
2. **LLM05/06 payloads are imported as-is.** garak's carrier templates are not bundled in PyRIT
   (verified: local payload files are bare `{value}`; remote garak sets are flat one-row strings), so
   there is nothing of garak's to vendor and no delivery wording is authored here. The payload is the
   prompt; the output scorer judges whether the reply reflects/echoes attacker content unescaped.
3. **LLM10 is a detector, not a pack** — a deterministic reply-length / latency threshold, auxiliary
   on any pack. No attack prompts, so no authoring.
4. **LLM08 is a per-bot planted-marker template.** A generic dataset cannot test cross-user retrieval;
   the owner plants a marker in another user's document and the check is `must_not_contain` that marker.
5. **LLM03/04 are a review checklist** in `COVERAGE.md`, labelled not-prompt-testable.
6. Everything reuses the v0.2 importer machinery (loader, map, `importer.py`, `suite import`,
   deterministic atomic writes, the adapters boundary). Only `adapters/` imports pyrit.

## 4. Phases (each gets its own implementation plan)

- **Phase A — LLM05 + LLM06** (this spec details it): import the four local garak payload datasets
  as-is; wire `shell_command_output` into the detector registry (`xss_output`, `markdown_injection`
  already wired); add their map rows; add stale-file pruning (now load-bearing — see §6).
- **Phase B — LLM09:** vendor PyRIT's `garak_pypi_packages` registry list once into a committed data
  file; wire `PackageHallucinationScorer`; import `package_hallucination` with stub×task substitution.
- **Phase C — LLM01:** add `StaticPromptInjectionScorer` as an auxiliary detector on the extraction set.
- **Phase D — LLM10:** a new `resource_consumption` detector (reply chars / latency over a per-endpoint
  threshold), usable as a `forced` auxiliary on any run.
- **Phase E — LLM08:** a planted-marker template (an `endpoints/` + `prompts/` skeleton + docs).
- **Phase F — LLM03/04:** the review checklist and the regenerated all-ten `COVERAGE.md`.

Build order A → B → C → D → F, with E any time (docs/template). Phase A is planned now; the rest
follow as their own specs/plans.

## 5. Phase A requirements (LLM05 + LLM06)

- **A1.** `importer_map.py` gains four rows: `web_html_js`→(LLM05, `xss_output`), `example_domains_xss`
  →(LLM05, `xss_output`), `markdown_js`→(LLM05, `markdown_injection`), `access_shell_commands`→(LLM06,
  `shell_command_output`); all `canary_check=False`; each with a default `pass_if`.
- **A2.** `adapters/detectors.py` wires `ShellCommandOutputScorer` under the name `shell_command_output`;
  `suite.prompts.DETECTOR_NAMES` gains `shell_command_output`. (The map/registry sync test from v0.2
  then guards it.)
- **A3.** `suite import --source garak` now writes `LLM05.yaml`, `LLM06.yaml`, `LLM07.yaml` +
  `COVERAGE.md`; each LLM05/06 prompt carries exactly its output detector (no canary), so it is
  rule-judged (never routed to review for lack of a check, never a silent Pass).
- **A4.** Ids stay `BASE-<CAT>-<dataset>-NNN`; determinism and per-file atomic writes unchanged.
- **A5.** `COVERAGE.md` now marks LLM05 and LLM06 covered (and LLM09/01/10/08/03/04 per §2, with
  the later-phase / template / checklist wording).

## 6. Stale-file pruning (now load-bearing)

v0.2's final review deferred this: `suite import` does not remove files already in `--out`. With one
category that was harmless; with a changing category set it is not — a shrinking map would leave a
stale `LLM0x.yaml` that a later run would pick up. **Phase A adds pruning:** before writing, the
importer removes the generated files it manages in `--out` (the `LLM*.yaml` it is about to write for
this source, and `COVERAGE.md`), or writes the whole set into a freshly-cleared managed subtree, so
the output is exactly the current map's product. It must not delete unrelated files a user placed
there (only files matching the generated pattern). A test covers: a stale `LLM99.yaml` from a prior
run is gone after re-import.

## 7. Testing (Phase A, TDD, no network, no attack text)

- Benign fixture datasets for the new shapes (payload-shaped but benign — e.g. an innocuous HTML
  snippet, a harmless command string); loaded through the real loader.
- `importer_map` sync test (already present) now also guards the four new rows and `shell_command_output`.
- `adapters/detectors`: `shell_command_output` trips on a benign shell-command-output string and is
  clean on ordinary prose; `pyrit_detectors()` keys == `DETECTOR_NAMES`.
- `importer`: `suite import` writes LLM05.yaml + LLM06.yaml + LLM07.yaml; each LLM05/06 prompt has its
  detector and no canary; byte-identical re-run; stale-file pruning (§6).
- `cli`: the summary now reads "across 3 categories".

## 8. Risks

- **Payloads-as-is may be refused.** A bot that ignores a raw payload yields `Pass (rule)` that is not
  proof of safety. `COVERAGE.md` and the validation doc state this; a realistic carrier flow is a
  later option (owner-authored carriers).
- The output scorers' false-positive/negative behaviour is PyRIT's, used as-is (spec §8 of v0.1).

## 9. Validation (Phase A, Executed)

Regenerate the baseline (LLM05/06/07), `suite run` against the lab bot, inspect `report.html` — the
By-OWASP table now shows three categories. Label every result Executed / Not Testable.
