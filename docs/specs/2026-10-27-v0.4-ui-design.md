# chatbot-redteam v0.4 — Web UI (Read + Review)

Date: 2026-10-27
Status: draft for review
Author: Sahil Otavanekar (with Claude)

Gives the framework a browser face. v1 is a **thin, read-and-review layer over the existing
engine** — it lets the operator *see* runs and reports without opening `results/` folders or raw
CSV, and do the human-review step in the browser instead of hand-editing `review.csv`. Runs are
still started from the CLI. Builds on `main` (v0.1 engine + v0.2 importer + v0.3 Phase A).

## 1. Purpose

The engine already produces everything a report needs — `report.html`, `matrix.csv`, `review.csv`,
`compare.md` — inside each git-ignored run folder. Two things are still awkward:

1. **Reading** a run means finding its folder and opening files one at a time; comparing runs or
   seeing OWASP coverage means cross-referencing by hand.
2. **Reviewing** the queued attempts means editing `review.csv` in a spreadsheet, then running
   `suite finalize` on the CLI.

The UI makes both pleasant in a browser, **without moving any logic out of the engine**. It is a
presentation layer: it reads what the engine computed and writes review verdicts back through the
engine's own `review.csv` + `finalize` path.

## 2. Scope

**In scope (v1 = Read + Review):**

- List all runs found under `results/`, with status and headline verdict counts.
- View one run: the report (totals, By-OWASP table, per-prompt verdicts), the evidence a report
  already shows (redacted), and run facts.
- A **COVERAGE view**: the ten OWASP LLM categories, which are present in this run, and the legend
  that "Pass (rule) is not proof of safety".
- A **compare view**: baseline vs run deltas (reuses `compare_runs`).
- A **review flow**: list the attempts the engine judged *Needs review*, show each reply against its
  `pass_if`, let the reviewer mark Pass/Fail + a note, write it back to `review.csv`, and run
  **Finalize** (the engine's `finalize`) to merge verdicts and regenerate the final reports.
- A **JSON API** (`/api/v1/*`) under the HTML views, backed by the same service layer, so a React
  frontend can replace the views later without touching logic.

**Out of scope (YAGNI — deferred to a later "operator console" phase, §13):**

- Triggering `suite import` or `suite run` from the browser; live progress / streaming / websockets.
- Authentication / login / multi-user; the v1 server is a single-operator localhost tool.
- Revealing the raw (un-redacted) reply.
- Editing prompt packs or endpoint YAML in the browser.

## 3. Key decisions

1. **The engine does not change.** `src/suite/web/` is the only new code. It imports engine
   functions; it adds no judging, redaction or report logic of its own.
2. **One service layer, two faces.** `web/service.py` is the only module that touches `results/`
   and calls the engine. Both the JSON API (`api.py`) and the HTML views (`views.py`) call it, so
   they are two renderings of one set of data — which is what lets React replace the views later.
3. **Review is a round-trip over the engine's own `review.csv`.** The review queue, the `pass_if`
   text and the **full redacted reply** are read from the run's `review.csv` (the engine writes the
   whole reply there, not an excerpt). Verdicts are written back into the same file, so a reviewer
   can start in the browser and finish on the CLI, or the reverse. **Finalize** calls the existing
   `finalize(run_dir)` unchanged.
4. **Redaction is the engine's, reused as-is.** Everything the UI shows comes through
   `build_report_data` (redaction gated on `run["redact"]`, default on) or through `review.csv`
   (already redacted when written). The UI never reads raw `reply_text` from `evidence.db`.
5. **Local-only, no auth, no target contact.** The server binds `127.0.0.1`. It never sends a
   prompt to any target — it only reads results already produced — so the "authorised targets only"
   rule is not even exercised by the web layer in v1.
6. **FastAPI + HTMX + Jinja2**, JSON API underneath (the 2026-10-23 decision). Jinja2 is already a
   dependency (via `report.py`); `fastapi` + `uvicorn` are added and pinned; `htmx.min.js` is
   vendored, pinned, and served locally (no CDN).

## 4. Architecture

```
src/suite/              engine — UNCHANGED, the single source of truth
  report.build_report_data / write_reports   read + render run data (redacted)
  review.finalize                            merge review.csv verdicts, regenerate final reports
  compare.compare_runs                       baseline-vs-run deltas
  prompts.OWASP_LLM_2025                      the category registry (drives COVERAGE)

src/suite/web/          NEW — thin presentation layer
  service.py            the ONLY module that reads results/ and calls the engine.
                        Returns plain dataclasses/dicts (view models), no FastAPI types.
  api.py                FastAPI APIRouter, prefix /api/v1 → JSON
  views.py              FastAPI APIRouter → HTMX/Jinja2 HTML (full pages + fragments)
  app.py                create_app(settings) -> FastAPI: mounts routers, templates, static
  settings.py           WebSettings: results_dir, host (default 127.0.0.1), port
  templates/            base.html, runs.html, run.html, coverage.html, compare.html, review.html,
                        and HTMX fragments (_review_item.html, _runs_rows.html, …)
  static/               htmx.min.js (vendored, pinned), app.css (minimal)
```

The dependency arrow points one way: `web/ → suite/`. Nothing under `suite/` imports `web/`. A
boundary test enforces that `web/service.py` is the only `web/` module that imports the engine's
read/write/finalize/compare functions, mirroring the PyRIT adapter boundary test.

### View models (what `service.py` returns)

`service.py` adapts engine dataclasses into small view models so the templates and the JSON API
share one shape and neither depends on FastAPI or engine internals:

- `RunSummary(run_id, endpoint_name, status, started_at, finalized, totals: dict[str,int])` — one
  per run folder, for the list view.
- `RunDetail` — wraps the engine's `ReportData` (totals, categories, prompts) plus `run_facts`.
- `ReviewItem(attempt_id, prompt_id, category, hint, pass_if, prompt, reply, verdict, note)` — one
  per `review.csv` data row (the reply is the full redacted text).
- `CompareView(baseline_id, run_id, rows: list[CompareRow], counts)`.
- `CoverageRow(category_id, title, present: bool, prompt_count)` — one per `OWASP_LLM_2025` entry.

## 5. Routes

Each HTML view has a JSON sibling backed by the same `service.py` call (contract: same data).

| Method + path (HTML) | JSON sibling | Service call | Shows |
|---|---|---|---|
| `GET /` | `GET /api/v1/runs` | `list_runs()` | all runs, newest first, with status + counts |
| `GET /runs/{id}` | `GET /api/v1/runs/{id}` | `get_run(id)` | the report: totals, By-OWASP, per-prompt |
| `GET /runs/{id}/coverage` | `GET /api/v1/runs/{id}/coverage` | `coverage(id)` | the ten categories, present/absent, legend |
| `GET /runs/{id}/review` | `GET /api/v1/runs/{id}/review` | `review_queue(id)` | the Needs-review queue, each with pass_if + reply |
| `POST /runs/{id}/review/{attempt_id}` | `PUT /api/v1/runs/{id}/review/{attempt_id}` | `set_review_verdict(...)` | writes one verdict+note into `review.csv`; returns the updated row fragment |
| `POST /runs/{id}/finalize` | `POST /api/v1/runs/{id}/finalize` | `finalize_run(id)` | calls `finalize`; returns applied/pending or the ConfigError text |
| `GET /compare?baseline={id}&run={id}` | `GET /api/v1/compare?...` | `compare(baseline, run)` | the compare table |

`{id}` is a run-folder name; the service resolves it under `results_dir` and rejects any id that is
not a direct child directory of `results_dir` (no path traversal — §10).

## 6. Read path (no recompute, ever)

- `list_runs()` lists the immediate subdirectories of `results_dir`, reads each `run.json`
  (`read_run_json`) for status / endpoint / timestamps / `finalized_at`, and derives headline
  counts cheaply. A folder without a readable `run.json` is listed as *unreadable*, not crashed on.
- `get_run(id)` calls `build_report_data(run_dir, final=finalized)` — `final=True` when
  `run.json` has `finalized_at`, else `False` — and returns it wrapped as `RunDetail`. The verdicts,
  redacted replies and By-OWASP rows are exactly what `report.html` would show. No re-judging.
- `coverage(id)` iterates `OWASP_LLM_2025.items()`, marking a category present when the run has at
  least one prompt in it, so **Phase B+ categories appear with zero UI changes**. It carries the
  `VERDICT_LEGEND` so the page repeats "Pass (rule) is not proof of safety".
- `compare(baseline, run)` calls `compare_runs(baseline_dir, run_dir)` and renders the rows. Both
  sides are read as final (that is `compare_runs`' own rule).

## 7. Review path (the one interactive piece)

The engine writes `review.csv` in a draft report with columns `attempt_id, prompt_id, category,
hint, pass_if, prompt, reply, verdict, note`, where `reply` is the **full redacted** reply and the
rows are the attempts judged *Needs review*. The UI treats this file as the source and sink:

1. **`review_queue(id)`** reads the run's `review.csv` into `ReviewItem`s (it does not re-derive the
   queue; it shows the file the reviewer would otherwise edit). If `review.csv` is absent (e.g. the
   run was already finalized, or had nothing to review), the queue is empty and the page says so.
2. **`set_review_verdict(id, attempt_id, verdict, note)`** rewrites `review.csv` with the matching
   row's `verdict` set to `pass`/`fail`/`""` and `note` set to the typed note (passed through
   `report.csv_cell` so a note starting like a formula stays inert — the same neutralisation the
   engine uses; `review.finalize` already strips that mark back off). Every other cell is written
   back verbatim. The UI only ever writes `pass`, `fail` or blank, so it cannot create a row
   `finalize` would reject. Writes are atomic (temp file + replace), matching the engine's style.
3. **`finalize_run(id)`** calls `finalize(run_dir)`. On success it returns `FinalizeResult`
   (`applied`, `pending`) and the regenerated final reports are on disk; the run detail view now
   reads them. On `ConfigError` (a bad sheet, a locked report file on Windows) it returns the
   error's text for the page to show — nothing is half-applied, because `finalize` is all-or-nothing.

This keeps the browser and the CLI perfectly interchangeable: both read and write the one
`review.csv`, and both finalize through the one `finalize`.

## 8. Launch

A new CLI subcommand, consistent with the existing `suite` commands:

```bash
uv run suite web --results results --host 127.0.0.1 --port 8787
```

It checks the port is free first (the hard rule), then runs uvicorn with the app from
`create_app(WebSettings(...))`. `--results` defaults to `results/`. `--host` defaults to
`127.0.0.1`; binding elsewhere is possible but prints a one-line warning that there is no auth.

## 9. Dependencies

- Add `fastapi` and `uvicorn`, both pinned (exact versions chosen at build time, pinned in
  `pyproject.toml`). `jinja2` is already present (via `report.py`). `httpx` is already present and
  gives FastAPI's `TestClient` its transport.
- Vendor `htmx.min.js` (pinned version) into `src/suite/web/static/`; no CDN, no network at runtime.
- No new runtime secret, no `.env` read by the web layer.

## 10. Error handling & safety

- **Path traversal:** a run id must resolve to a direct child directory of `results_dir`; anything
  else is a 404. Ids are never joined into a path without that check.
- **Missing / malformed run:** a folder without `run.json` or `evidence.db` is shown as unreadable
  in the list and 404/placeholder on detail — never a 500.
- **Redaction:** only redacted text reaches a template (via `build_report_data` or `review.csv`).
  The web layer has no code path that reads raw `reply_text` from `evidence.db`.
- **Untrusted replies stay inert:** Jinja2 autoescape is on; nothing is marked `safe`. A reply is
  rendered as text, never as HTML — the same stance `report.html.j2` already takes.
- **No secrets rendered:** run facts show only the endpoint *name* (as `report.run_facts` already
  limits), never the endpoint block or any `.env` value.
- **Finalize failures** surface the engine's `ConfigError` text verbatim; the UI adds no new
  failure modes to finalization.

## 11. Testing (TDD, no network)

Driven by FastAPI's `TestClient` against a fixture `results/` directory built with the existing
`tests/factories.py` / evidence helpers. No real server, no target, no attack text.

- **service (read):** `list_runs` finds fixture runs and reports their status/counts; an unreadable
  folder is listed, not raised. `get_run` returns the same verdict totals as `build_report_data`.
  `coverage` lists every `OWASP_LLM_2025` category and marks present/absent correctly. `compare`
  matches `compare_runs`.
- **service (review):** `review_queue` reads a fixture `review.csv` into items with the full reply.
  `set_review_verdict` writes exactly the expected row back (other cells untouched; note neutralised).
  `finalize_run` on a filled sheet calls `finalize`, returns applied/pending, and the final reports
  appear; on a bad sheet it returns the ConfigError text and changes nothing.
- **views:** each page returns 200 and contains its key data; a reply containing `<script>` is
  HTML-escaped in the response (inert-rendering test).
- **api ↔ views contract:** the JSON sibling and the HTML view are built from the same service call
  (assert the JSON payload matches the view model the template received).
- **security:** a traversal id (`../`, an absolute path, a sibling file) is 404; only redacted text
  appears in responses.
- **boundary:** `web/service.py` is the only `web/` module importing the engine's
  read/finalize/compare functions.

Every result is labelled **Executed / Design-only / Not Testable**.

## 12. Risks

- **Long runs aren't visible live in v1.** Because the UI doesn't trigger runs, a run in progress is
  only seen by refreshing the list (it reads `run.json` status). Acceptable for v1; live progress is
  the operator-console phase. The list view states a run's status honestly (running/complete/aborted).
- **`review.csv` concurrent edits.** If someone edits `review.csv` in a spreadsheet *and* in the
  browser at once, last write wins. v1 is single-operator; the write is atomic, so the file is never
  corrupted, only overwritten. Documented, not guarded.
- **No auth.** Binding to anything but `127.0.0.1` exposes unauthenticated read access to evidence;
  the launch command warns, and the default is localhost. Auth is a later phase.

## 13. Future phases (operator console, not built here)

- Trigger `suite import` / `suite run` from the browser, with background tasks and a live progress
  view (the ~90-minute lab run is why this needs real job handling).
- Auth + multi-user, so teammates can review the same run; this turns the read-only localhost tool
  into a shared service.
- A React frontend over the same `/api/v1`, replacing the Jinja2 views.

## 14. Validation (Executed, at build end)

Point the server at a real `results/` folder from an earlier lab-bot run, open each view, do a
review in the browser, Finalize, and confirm the regenerated `report.html` matches a CLI `finalize`
of the same run. Label every check Executed / Design-only / Not Testable in a `docs/validation/`
note.
