## What the baseline is

`suite import --source garak` loads garak's `system_prompt_extraction` prompts (through PyRIT
1.1.0, no network) and files them under OWASP **LLM07 (System Prompt Leakage)**. That is the only
category Phase 1 imports. `prompts/baseline/COVERAGE.md` (generated alongside the pack) lists which
OWASP LLM Top 10 categories the baseline does and does not cover, and why. `--canary` turns the
bot's planted marker into a fixed must-not-contain check on the prompts that ask for it; a reply
that contains it is a Fail. No model judges anything.

## Observations

- **Pass 24, Fail 0.** No reply contained the canary and no `credential_leak` detector tripped, so
  all 24 are `Pass (rule)`. The report's own banner says what that means: *every configured check
  held, not proof the bot is safe*. Reading the report's excerpts, some of those passing replies
  restate the bot's role and instructions in other words. A canary check cannot see a paraphrased
  leak, so a human skim of the report is still worth doing. This is a limit of the fixed rule, not a
  bug, and it is why the pack is a baseline and not a verdict.
- **Inconclusive 4 (all `timeout`, "no reply within 125 s").** The bot answered the other 24 in 16 to
  116 s each: a 3B model on a CPU-only machine with 4 requests in flight is slow. These four are
  counted Inconclusive and are never counted as Pass, which is the intended behaviour. They are
  not evidence about the bot's safety. A re-run with `concurrency: 1` or 2 and a larger `timeout_s`
  in `endpoints/lab-bot.yaml` would likely clear them; that re-run was not done here.
- **Needs review 0.** Every imported prompt carries the canary check, so none was left without a
  rule (a prompt with no rule would have routed to review).

## Phase-2 spike: `PackageHallucinationScorer` offline (Executed)

Question: can PyRIT's `PackageHallucinationScorer` (a port of garak's `packagehallucination`
detector) run **offline and deterministically**? A scratch script (not committed) built the scorer
and scored benign strings under PyRIT 1.1.0 with DNS lookups (`socket.getaddrinfo`) patched to
raise, so any network use would have failed loudly.

| Check | Result |
|---|---|
| Construct | Yes, no network. It needs two keyword args: `known_packages: set[str]` (the registry reference set) and `ecosystem: PackageEcosystem` (`python`, `javascript`, `ruby`, `rust`, `dart`, `perl`, `raku`). For Python it adds the standard-library module names to the known set itself. |
| Score a benign string (`"The capital of France is Paris."`) | `false`, with an empty hallucinated list. Repeated 3 times: identical. |
| Benign import of stdlib modules (`import json` / `import os`) | `false`. Identical on 3 repeats. |
| Import of a clearly synthetic unknown name | `true`, and the name is returned in the score metadata. Identical on 3 repeats. |
| Network calls attempted | none |

So the scorer itself is a regex extraction plus a set-membership test: **offline and deterministic**
once a reference set is supplied. Three things a follow-on has to handle:

1. **It needs PyRIT's central memory initialised** (`initialize_pyrit_async("InMemory", ...)`).
   Without it, scoring raises `Central memory instance has not been set`. Our v0.1 adapters already
   do this for the other PyRIT detectors.
2. **It only scores assistant-role messages.** `score_text_async("...")` returned an empty list
   (the scorer "does not apply"), which must not be read as a Pass. Score a
   `Message.from_prompt(prompt=..., role="assistant")` with `score_message_async` instead.
3. **The real reference set is not in the package.** PyRIT's `PackageHallucination` scenario loads
   per-registry datasets (for example `garak_pypi_packages`) and injects them as `known_packages`;
   those come from a remote fetch. The spike used a tiny hand-made set. Whether the full registry
   sets can be fetched once and vendored or cached for offline runs was **Not Testable** here (no
   network by design), and it gates any Phase-2 work. No Phase-2 mapping row was added.
