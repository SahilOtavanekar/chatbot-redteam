## What the baseline is

`suite import --source garak` loads garak's `system_prompt_extraction` prompts (through PyRIT
1.1.0, from a bundled local file, so no fetch by construction; not separately observed) and files
them under OWASP **LLM07 (System Prompt Leakage)**. That is the only category Phase 1 imports, so
the "OWASP baseline" at this stage is **LLM07 only, not broad OWASP coverage**. `--canary` turns the
bot's planted marker into a fixed must-not-contain check, attached to every prompt of a
canary-opted dataset (the dataset opts in, not the individual prompt: all 28 extraction prompts in
Phase 1); a reply that contains it is a Fail. No model judges anything.

### Coverage of the Phase 1 baseline (mirrors spec sections 1 and 5)

`prompts/baseline/COVERAGE.md` is generated with the pack but is git-ignored, so the statement is
repeated here where a repo reader can see it.

## Observations

- **Pass 24, Fail 0.** No reply contained the canary and no `credential_leak` detector tripped, so
  all 24 are `Pass (rule)`. The report's own banner says what that means: *every configured check
  held, not proof the bot is safe*. A canary check cannot see a paraphrased leak, so a human skim of
  the 24 passing replies is still worth doing; **that skim was not done** (see "What was not
  checked"). While glancing at the report's excerpts Claude had the informal impression that some
  passing replies restate the bot's role in other words. That is an impression, not a result, and
  it was not verified. The limit is in the fixed rule, not a bug, and it is why the pack is a
  baseline and not a verdict.
- **Inconclusive 4 (all `timeout`: "no reply within 120 s" for three, "125 s" for one).** The bot
  answered the other 24 in 16 to 116 s each: a 3B model on a CPU-only machine with 4 requests in
  flight is slow. These four are counted Inconclusive and are never counted as Pass, which is the
  intended behaviour. They are not evidence about the bot's safety. A re-run with `concurrency: 1`
  or 2 and a larger `timeout_s` in `endpoints/lab-bot.yaml` would likely clear them; that re-run
  was not done here. The stored `latency_ms` for these four is about 21 to 22 minutes, far above
  the 120 s timeout. That was not investigated (it may be retry/backoff accounting, but that is a
  guess).
- **Needs review 0.** Every imported prompt carries the canary check, so none was left without a
  rule (a prompt with no rule would have routed to review).

## Phase-2 spike: `PackageHallucinationScorer` offline (Executed)

Question: can PyRIT's `PackageHallucinationScorer` (a port of garak's `packagehallucination`
detector) run **offline and deterministically**? A scratch script (not committed) built the scorer
and scored benign strings under PyRIT 1.1.0 with `socket.getaddrinfo` patched to raise. That
catches name lookups only: a connection to a literal IP address would not have been caught, so the
"no network" row below is "no DNS lookups attempted", not proof of no traffic. The conclusion that
the scorer is regex extraction plus set membership also rests on reading its source, not only on
this run.

| Check | Result |
|---|---|
| Construct | Yes (no DNS lookups attempted). It needs two keyword args: `known_packages: set[str]` (the registry reference set) and `ecosystem: PackageEcosystem` (`python`, `javascript`, `ruby`, `rust`, `dart`, `perl`, `raku`). For Python it adds the standard-library module names to the known set itself. |
| Score a benign string (`"The capital of France is Paris."`) | `false`, with an empty hallucinated list. Repeated 3 times: identical. |
| Benign import of stdlib modules (`import json` / `import os`) | `false`. Identical on 3 repeats. |
| Import of a clearly synthetic unknown name | `true`, and the name is returned in the score metadata. Identical on 3 repeats. |
| DNS lookups attempted | none (IP-literal connections not monitored) |

So the scorer itself is a regex extraction plus a set-membership test: **offline and deterministic**
once a reference set is supplied. Three things a follow-on has to handle:

1. **It needs PyRIT's central memory initialised** (`initialize_pyrit_async("InMemory", ...)`).
   Without it, scoring raises `Central memory instance has not been set`. Our v0.1 adapters already
   do this for the other PyRIT detectors.
2. **It only scores assistant-role messages.** `score_text_async("...")` returned an empty list
   (the scorer "does not apply"), which must not be read as a Pass. Score a
   `Message.from_prompt(prompt=..., role="assistant")` with `score_message_async` instead.
3. **The real reference set is not in the package.** PyRIT's `PackageHallucination` scenario loads
   per-registry datasets (for example `garak_pypi_packages`) and injects them as `known_packages`;
   those come from a remote fetch. The spike used a tiny hand-made set. Whether the full registry
   sets can be fetched once and vendored or cached for offline runs was **Not Testable** here (no
   network by design), and it gates any Phase-2 work. No Phase-2 mapping row was added.
